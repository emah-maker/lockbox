# FRAIM Skill: slo-design

## Skill Input
- Service description: what the service does, who its users are, and what "good" looks like from the user's perspective.
- User journey map: the critical user actions the service must support (e.g., login, checkout, API call, report load).
- Monitoring stack: available telemetry sources (Prometheus, Datadog, CloudWatch, custom metrics) and metric names.
- Incident history (optional): past outages or degradation events with duration and user impact.
- Existing alert configuration (optional): current threshold-based alerts, PagerDuty policy, or on-call runbooks.

## Skill Output
- **SLI Definitions**: For each user journey, the specific metric that measures user experience. Format: "SLI: [metric description]. Good event: [condition]. Total events: [population definition]."
- **SLO Targets**: For each SLI, the target percentage of good events over the rolling window. Format: "SLO: [SLI name] ≥ [target]% over [window]."
- **Error Budget**: The maximum allowable bad events within the window. Expressed in: percentage (100% − target), event count (at median traffic), and time equivalent (minutes of 0%-good-request behavior that exhausts the budget).
- **Burn Rate Alert Rules**: Fast-burn alert (1-hour window, 14.4× consumption rate) and slow-burn alert (6-hour window, 6× consumption rate). Both must fire before the budget is half-consumed.
- **SLO Dashboard Specification**: The four panels every SLO dashboard must show: current good event rate, error budget remaining (%), error budget burn rate (current vs. 1× pace), and SLO compliance status (in-window or breached).
