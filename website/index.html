Phone Box

A lockbox that physically holds a phone shut for a set focus session. You close the lid, set a time on its touchscreen, and a servo latch keeps it closed until the timer runs out. It works on its own with no account and no connection, and an optional iOS companion app pairs over Bluetooth Low Energy for live status and focus stats.

Motivation

Software blockers can be turned off with one settings toggle, and the phone stays in your hand the whole time. Commercial lockboxes solve that but are usually transparent, use a mechanical dial, and offer either no way out or a weak one. I wanted a box that enforces the session physically while still giving a deliberate way out in an emergency.

Design goals

  • Physical enforcement. The latch, not software on the phone, keeps the session.
  • A controlled exit. A tunable press-count override instead of a bypass or no exit at all.
  • Self-contained. All core functions run on the box with no app, account, or network.
  • Opaque and rechargeable. No seeing notifications through the case, and USB-C charging.

2Operation

Lock cycle

  1. Close the lid. The lid presses a sensor button and the servo latches. No countdown runs yet.
  2. Set the time. Swipe on the touchscreen to set hours, minutes and seconds, up to 9 h 55 min.
  3. Tap LOCK. The countdown starts. While it runs, the clock is the only screen available.
  4. Session ends. When the timer expires the latch releases and the session is logged.

Firmware states

The controller in lock_controller_states.py is a small state machine. The app receives the current state verbatim over BLE.

StateLatchMeaning
idleOpenNo session. Lid open or not yet detected.
closedLatchedLid sensor tripped and servo latched; waiting for LOCK.
pickingEitherOn-box tag picker shown before a session starts.
confirmingEitherConfirm or change a session topic the app sent ahead of time.
runningLatchedCountdown active. Only the override or the timer ends it.
doneReleasingSession over by timer, override, or app unlock. Completed runs are logged.

Emergency override

Pressing the override button a set number of times releases the latch early. The count is 25 by default and can be set from 5 to 500 in steps of 5. Every release is written to on-device memory, so using it is never silent. If more than a second passes between presses (adjustable from 0.3 to 10 s), the count resets to zero, so the presses have to be one deliberate sequence rather than a tally built up over time.

The iOS app can also unlock the box automatically when a phone call comes in. This is off by default. Otherwise, the press-count override is the only way to end a session early.

Power & fuel gauge

The ESP32-S3 board has no fuel gauge, so a raw ADC voltage was the only battery signal. I added a MAX17043 breakout and modified it by hand: cutting the traces that tied its 3 V rail to the battery rail, then soldering and crimping it in. It shares the touchscreen’s I2C bus at address 0x36, so it uses no extra GPIO and reports a real state of charge.

4Firmware

CircuitPython on the ESP32-S3, about 8,000 lines across roughly 30 modules in firmware/lib: the controller and its state machine, the servo, power and battery handling, BLE, settings, logging, and the touchscreen UI.

Touch driver

The AXS5106L touch controller had no CircuitPython driver, so the box runs a custom one over I2C (axs5106l.py). It includes a debounce fix for frames the controller intermittently drops mid-touch.

Persistence and brownout recovery

Settings, schedules, routines and focus streaks live in the microcontroller’s non-volatile memory rather than a host-writable filesystem, so state survives a full power cut. A brownout counter in the same memory drives automatic recovery if the servo’s inrush current browns out the board mid-lock.

5Companion app

An iOS app built with React Native (Expo), backed by Firebase. It is optional: the box does everything in sections 2–4 without it. Two small native iOS modules, call-observer and background-wake, cover what React Native cannot reach.

BLE interface

One custom GATT service. The UUIDs and payload shapes are defined twice, in the firmware’s lock_config.py and the app’s protocol.ts, and kept in sync by hand.

Features

  • Live status. Lock state, countdown and battery from the box.
  • Focus stats. Session history, streaks, and time per topic.
  • Goals and calendar. Focus goals with reminders, and planned sessions.
  • Call unlock. Optional automatic release when a call comes in. Off by default.
  • Sync. Sessions sync through Firebase and are viewable on the web dashboard (sign-in required).

6Debugging log

Problems that only appeared on the physical device, and how they were resolved.

6.1

Intermittent servo failures

Locks failed intermittently, never in a way that could be reasoned about on screen. Running lock cycles on the bench until the pattern appeared showed two separate faults: the CPU clock scaling out from under the servo’s PWM timer, and a motor drawing close to an amp from a rail that could not supply it. The firmware now re-asserts 50 Hz on every move, and the servo runs from the battery rail with bulk capacitance instead of 3.3 V.

6.2

Dropped touch frames

The touch controller occasionally drops frames in the middle of a touch, which chopped taps and swipes into separate touches. The firmware now requires a few consecutive empty reads before treating a touch as released.

6.3

No real battery reading

With no fuel gauge on the board, the state of charge was a guess from ADC voltage. Fixed in hardware with the modified MAX17043 described in Power & fuel gauge.
